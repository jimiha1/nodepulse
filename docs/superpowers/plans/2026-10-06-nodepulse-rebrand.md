# NodePulse Rebrand Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename this app from ServerBox to NodePulse everywhere a user or the OS can see it — display name, icon, Android package name, deeplink scheme, HTTP user agents, Dart package name, and the GitHub repository — leaving feature behaviour untouched.

**Architecture:** Five ordered tasks, each one commit and independently revertable: (1) generate the new icon from a checked-in script, (2) change the display name and the strings that carry it, (3) move the Android package from `tech.lolli.toolbox` to `app.nodepulse` across Gradle, Kotlin, the manifest and the widget XML, (4) rename the Dart package `server_box` → `nodepulse`, (5) the remaining identifiers (deeplink scheme, user agents, version alignment, README, GitHub repo rename). Task 6 verifies on a device.

**Tech Stack:** Flutter 3.47 / Dart, Kotlin (Android), Python 3.9 (`py`) for the icon generator, Gradle.

## Global Constraints

- **Never run code formatters.** Formatting is deliberate; match the style of the file you edit.
- **Never hand-edit `*.g.dart` / `*.freezed.dart`** — regenerate instead.
- **Do not modify anything under `packages/`** (vendored submodules: fl_lib, fl_build, …).
- **`make` is NOT installed on this machine.** Run `flutter` / `dart` / `py` directly.
- **`crates/` and the root `Cargo.toml` were removed by an earlier trim** — there is no Rust pre-build step, despite what the Makefile says.
- **Do not start a second `flutter run`** — the app is usually already running from the user's IDE.
- **Exact new values, to be used verbatim:**
  - Display name: `NodePulse`
  - applicationId / namespace: `app.nodepulse`
  - Kotlin package root: `app.nodepulse` (directory `android/app/src/main/kotlin/app/nodepulse/`)
  - Dart package name: `nodepulse` (import prefix `package:nodepulse/`)
  - Deeplink scheme: `nodepulse`
  - Icon background: `#1A3D5C`; icon waveform: `#FFFFFF`
  - User agents: `NodePulse-Alert/1`, `NodePulse-Widget/2`, `NodePulse-DoH/1`
- **Version stays inherited:** `pubspec.yaml` version becomes `1.0.1799+1799` (aligned to the git commit count, which is what `fl_build` derives `BuildData.build` from). Do **not** reset it to `1.0.0` — `.github/workflows/build.yml` hard-validates that the tag, `BuildData.build` and the pubspec version all agree, and `AppUpdate` compares builds numerically.
- **Accepted cost, already agreed:** a new applicationId means a different app to Android. Old installs do not upgrade in place; site config, credentials, alert rules and home-screen widgets do not carry over.
- **Two identifiers are spelled on both the Dart and the Kotlin side and must end up equal.** Neither the analyzer nor the Kotlin compiler checks them against each other:
  - the MethodChannel prefix: `Miscs.pkgName` (`lib/data/res/misc.dart`) vs the literals in `MainActivity.kt`;
  - the deeplink scheme: `AppLink.scheme` (`lib/data/model/app/app_link.dart`) vs `LINK_SCHEME` (`MainActivity.kt`) vs the manifest.
  Each is changed by the task that owns that side, and each has a grep step that compares them.

### Task 1: Generate the new icon

**Files:**

**Interfaces:**
- Consumes: nothing.
- Produces: a re-runnable script. Later tasks do not depend on it, but the app icon is visible in Task 6's device check.

**Background the implementer needs:** this repo has **no drawing tool** (no ImageMagick, no Inkscape, no Node). Its existing icons are produced by checked-in scripts that write their output by hand — `scripts/gen_tray_icons.py` hand-writes a PDF, `scripts/theme-icons.py` hand-writes SVG. Follow that convention: write a Python script that emits the PNGs itself, so the artwork is reviewable code rather than an opaque binary.

The icon is an ECG heartbeat line: a horizontal line entering from the left, one sharp spike in the middle, exiting right. Drawn as a thick stroke with round caps and joins, in white, on a solid `#1A3D5C` background.

- [ ] **Step 1: Write the generator script**

Create `scripts/gen_app_icon.py`. It must:

1. Define the waveform in a **unit square** (0..1 on both axes) so every output size draws the same shape:

```python
# The waveform, in a unit square. A flat lead-in, one spike, a flat lead-out.
# The spike is deliberately narrow and tall: at 40 px the launcher shows, a
# gentler one would blur into a smudge.
WAVE = [
    (0.20, 0.50),  # lead-in start
    (0.36, 0.50),  # lead-in end
    (0.44, 0.28),  # spike up
    (0.58, 0.72),  # spike down, below the baseline
    (0.66, 0.50),  # back to baseline
    (0.82, 0.50),  # lead-out end
]
STROKE = 0.075          # stroke width, in unit-square terms
BG = (0x1A, 0x3D, 0x5C)  # #1A3D5C
FG = (0xFF, 0xFF, 0xFF)
```

2. Rasterise with **supersampling**: for each output pixel, sample the shape at a 4×4 grid and average, so the round caps and the diagonal spike are anti-aliased. Coverage is computed as "distance from the pixel centre to the polyline is within `STROKE/2`" — a distance-to-segment test over each of the five segments, plus the round caps at both ends. This is a few dozen lines of plain Python and needs no library.

3. Write PNGs with a hand-rolled encoder: `zlib.compress` over the raw scanlines (each row prefixed with a `0` filter byte), wrapped in `IHDR` / `IDAT` / `IEND` chunks with a CRC32 per chunk (`zlib.crc32`). RGBA, 8-bit.

4. Emit every output, and print each path with its byte size:

| Output | Size |
|---|---|
| `assets/app_icon.png` | 512×512 |
| `mipmap-mdpi/ic_launcher.png` | 48×48 |
| `mipmap-hdpi/ic_launcher.png` | 72×72 |
| `mipmap-xhdpi/ic_launcher.png` | 96×96 |
| `mipmap-xxhdpi/ic_launcher.png` | 144×144 |
| `mipmap-xxxhdpi/ic_launcher.png` | 192×192 |
| same five sizes | `ic_launcher_round.png` (same drawing) |
| same five sizes | `ic_launcher_monochrome.png` (same drawing) |
| 108×108 / 162×162 / 216×216 / 324×324 / 432×432 | `ic_launcher_foreground.png` |

The five `ic_launcher_foreground.png` sizes are the launcher icon sizes × 2.25 — that is the convention the current files use, and it is what keeps the adaptive icon's safe area correct. Verify against the existing files before overwriting:

```bash
py -c "
import struct, pathlib
for p in sorted(pathlib.Path('android/app/src/main/res').glob('mipmap-*/ic_launcher*.png')):
    w, h = struct.unpack('>II', p.read_bytes()[16:24])
    print(f'{p.parent.name:18} {p.name:32} {w}x{h}')
"
```

- **`ic_launcher_foreground.png` is drawn differently from the others**: it carries **no background fill** (transparent), and its waveform is scaled to the centre 66% of the canvas, because Android crops adaptive icons to a shape the launcher chooses. Drawing the waveform full-bleed here would get its ends clipped on a circular launcher.
- `ic_launcher.png`, `ic_launcher_round.png` and `ic_launcher_monochrome.png` are drawn full-bleed with the background filled. `ic_launcher_monochrome.png` is the Android 13+ themed-icon layer: **white waveform on transparent**, no background (the system supplies the colour).

`fl_build` derives `BuildData.build` from the git commit count and has a function that writes the matching pubspec version. Use it rather than editing by hand — it is the same code the release flow runs:

```bash
cd /d/flutter_server_box
```

- [ ] **Step 4: Regenerate `BuildData` so the new name lands**

`lib/data/res/build_data.dart` is a **tracked, generated** file, and `flutter build apk` does **not** regenerate it: `updateBuildData()` runs only when `fl_build` is invoked with the build-preparation flag (`-bp`) or the release flag (`-r`). So it needs its own step.

Rather than drive `fl_build`'s CLI (which proceeds into a real build), write the file the way `updateBuildData()` does. It derives exactly two fields — `name` from pubspec's `fl_build.appName`, `build` from `git rev-list --count HEAD` — and emits a fixed header:

```bash
cd /d/flutter_server_box
py - <<'PYEOF'
import re, subprocess, pathlib

pubspec = pathlib.Path('pubspec.yaml').read_text(encoding='utf-8')
name = re.search(r'^\s*appName:\s*(\S+)\s*$', pubspec, re.M).group(1)
count = subprocess.run(['git', 'rev-list', '--count', 'HEAD'],
                       capture_output=True, text=True, check=True).stdout.strip()

pathlib.Path('lib/data/res/build_data.dart').write_text(
    '// This file is generated by fl_build. Do not edit.\n'
    '// ignore_for_file: prefer_single_quotes\n'
    '\n'
    'abstract class BuildData {\n'
    f'  static const String name = "{name}";\n'
    f'  static const int build = {count};\n'
    '}\n',
    encoding='utf-8',
)
print(f'BuildData: name={name} build={count}')
PYEOF
grep -n "name = \|build = " lib/data/res/build_data.dart
```

Expected: `BuildData: name=NodePulse build=<count>`, and the grep shows `name = "NodePulse"` with the commit count.

**Stated plainly:** this reproduces `fl_build`'s output instead of running it, because running it drags in a full build. The header is verbatim, and the two fields are exactly the two it derives. ## Notes for the reviewer

- **Why the icon is a script:** this repo has no drawing tool, and its other icons are produced by checked-in generators (`gen_tray_icons.py`, `theme-icons.py`). A script keeps the artwork reviewable and re-runnable; a committed binary would not be.
- **Why the version is not reset:** `BuildData.build` comes from the git commit count, and CI validates tag ↔ build ↔ pubspec agreement. Resetting would break the release workflow and the update check. See the spec's §4.5.
- **Why only two ARB keys change:** the other ten `ServerBox` occurrences in each ARB belong to features removed by an earlier trim. Editing them would be translating a feature that does not exist.
- **The MethodChannel coupling is the subtlest part of this plan.** Dart and Kotlin each spell the channel name; Task 3 changes the Kotlin side and Task 4 the Dart side. They must agree, and nothing in the compiler enforces it — Task 4 Step 3 greps both.
